# 面接で説明する技術的ポイント

> **履歴注記(2026-11-13)**: 本文はAWS-B限定LIVE実証**前**の記録で、当時の状態(未デプロイ／LIVE NO-GO等)を保存している。AWS-Bは2026-11-12に限定LIVE実証を完了し、同日に対象Trialの停止・撤収を実施した。継続本番監視は未開始。最新の実証結果は [EVIDENCE_INDEX.md](EVIDENCE_INDEX.md) §0 を参照。過去の記録本文は書き換えていない。

各項目に「実測済み / オフライン検証のみ / 設計のみ」を付ける。LIVE未実施の項目を実測済みとして話さない。

## 1. 冪等性を「1回の条件付き書込み」に集約した(AWS-B)

- 課題: Scheduler→Lambdaは非同期で、同じイベントが複数回届く、遅れて届く、順序が入れ替わることがある。
- 設計: 制御項目への1回の `UpdateItem` に、稼働中か・世代・ポリシー版・`last_slot < slot` をまとめた。重複、逆順、停止後の到着は同じ書込みで失敗する。読んでから書く方式ではないので、停止と確保の競合に隙間が無い。
- 割り切り: 監視は周期的なので、取り逃した枠は再実行しない。leaseや再実行管理を持たない。確保したが結果の無い枠は UNKNOWN として表示する。
- 根拠: `src/aws_b/store.py`、`tests/aws_b/test_handler.py`(重複・逆順・停止競合・ack喪失)、`test_claim_mutations.py`(条件式の各節を外すと実際に二重probe等が起きることを確認)。
- 状態: **オフライン検証のみ**(擬似DynamoDBが実際の条件式を評価)。

## 2. 「証拠のない成功を出さない」を保存失敗時まで通した

- 結果の保存に失敗したら再probeせず、`Unpersisted` メトリクスを出す。読取側は「確保済み・結果なし」を UNKNOWN とする。
- 監視が沈黙した場合は Alarm の欠測=異常 で検知する。古いUPを現在の状態として表示しない(`view.py` の STALE)。
- 状態: **オフライン検証のみ**。

## 3. 停止を複数層に分け、何に依存しないかを明示した

- AWS-B: 制御項目(世代を進める)、Schedule無効化、同時実行数0。
- AWS-C: OS内タイマー(AWS APIに依存しない)、Watchdog Lambda(Worker・DynamoDBに依存しない)、通知(人)。
- Budgetsは通知であって停止機構ではない、と設計とテストの両方で扱っている(ガード面のテンプレートにBudgetアクションがあると契約テストが失敗する)。
- 「APIが受理した」と「止まったことを観測した」を別状態にした(`TERMINATE_REQUESTED` / `TERMINATED_VERIFIED` / `TERMINATE_UNCERTAIN`)。
- 状態: **オフライン検証のみ**(Describe失敗、Terminate失敗、DynamoDB不通、対象が複数の各ケース)。

## 4. 「再armしない」を運用規約ではなく構造で保証しようとした(AWS-C)

- 起動・再起動・停止の権限をどのロールにも与えない。Controllerは予約と参照のみ。
- スロットは一度消費したら解放しない。Workerは `RESERVED` のときしか開始しない。
- 終了はTerminate。インスタンスのスタックは更新禁止(更新による置換=2回目の起動を防ぐ)。
- 状態: **設計＋オフライン検証**。Terminate方式のLIVE適用は未承認。Gate C-02 は未解消のまま。

## 5. 脅威モデルによって出口制御の層を変えた

- AWS-B(自作の単機能コード、非信頼コンテンツを実行しない): VPC外、アプリ層のallowlist＋IP固定接続。ネットワーク層の強制ではないと明記。NAT Gatewayを置かない理由は費用(月数十ドル規模)と目的の不一致。
- AWS-C(ブラウザ=非信頼コードを実行): インスタンス内でUID別のiptables、Proxy、sandbox、seccomp。AWS層はinbound 0、IMDSv2・hop制限1、外向き443のみ。
- 状態: Bは**オフライン検証のみ**。Cの隔離はLocal(WSL2)で過去に実測、**EC2では未実測**。

## 6. 完全性と真正性を分けた

- 完全性: S3の条件付きPUT(上書き不可)、S3側SHA-256チェックサム、読戻し、既存manifestとの突合。
- 真正性: 既存のplan/receiptはプロセス内鍵のHMACで、鍵が消えると検証できない。KMS非対称鍵での署名を候補として実装(既定は無効)。
- 署名しても「描画条件が本物か」は証明しない。`PROFILE_UNATTESTED` / 品質UNKNOWN は固定で維持。
- 状態: **オフライン検証のみ**(KMSはHMACの代役で配線のみ確認)。

## 7. 既存資産を書き換えずにAWSへ持ち込んだ

- 既存の `src/`・`tests/`・`web/`・`infra/public_web/` は1ファイルも変更していない(テストで確認)。
- Windows固定のDockerランチャは、コンストラクタだけを差し替えるサブクラスで Linux に対応。隔離オプション・preflight・後始末は継承。
- Worker内のジョブ状態は既存SQLiteのまま。DynamoDBは制御面の記録だけ。SQLiteトリガーの移植を避けた。
- 公開前の再検証は既存の読取専用プランナ `plan_recovery` をそのまま使用。過去のM5由来証拠のコピー71ファイルで CONSISTENT を**実測**。

## 8. IaCを「壊すと落ちるテスト」で守った

- 各テンプレートに、安全性の性質を1つずつ壊す変異テストを付けた(ガード約28、AWS-B 31、AWS-C 58)。
- テンプレートとコードの食い違いもテストする(Scheduleのイベント文字列をハンドラのパーサに通す、環境変数名、タグキー、3層のイベント寿命が同じ値か)。
- 起動スクリプトは、最初のコマンドがOSタイマーであること、全終了経路で電源断すること、実行時にパッケージを取得しないこと、イメージをダイジェストで取得することを検査。
- 限界: ローカルの構造検査であり、AWSがテンプレートを受理する保証ではない。

## 9. 失敗を記録として残した

- BuildKitの想定外通信、UAC待ちによる停止、時計ずれによるTLS失敗などを `EVIDENCE_INDEX.md` に残し、AWS側の設計判断(ダイジェスト固定、実行時インストールなし、TLS検証を無効化しない)へ結び付けた。
- 既存テストの基準実行で見つかった1件の不整合は、直さずに記録した(既存資産の変更は承認事項のため)。

## 聞かれそうな質問への答え方

| 質問 | 答えの要点 |
|---|---|
| なぜSQS/DLQを使わないのか | 監視は周期的で再実行に価値が無い。再試行0＋枠の確保で足りる。失敗はメトリクスで可視化 |
| なぜStep Functionsではないのか | 状態は「確保→記録」の2段で、DynamoDBの条件付き書込みで表現できる |
| なぜFargate/Lambdaでブラウザを動かさないのか | 既存の隔離はユーザー名前空間sandboxとNET_ADMINを使うヘルパーに依存する。使えない環境では `--no-sandbox` が必要になり、既存の安全設計を捨てることになる(要公式確認) |
| CloudWatch Syntheticsでよいのでは | 管理型で妥当な選択肢。今回は冪等性と停止の設計を示す目的で自作を選んだ |
| 本当に動くのか | AWS-Aは公開済み(過去報告)。ガード/B/Cは**オフライン完成・LIVE未検証**。未確認事項は `OPEN_ITEMS.md` に列挙 |
