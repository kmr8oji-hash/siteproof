# メール通知（SMTP）と長期運用の部品

SiteProof の通知は2段階です。(1) 監視の結果は、必ず**アプリの通知**として記録されます（`<site>/notifications.jsonl`、従来どおり）。(2) その通知を**メールでも**受け取りたい場合だけ、署名付きの許可と明示的な操作で、別のチャネルとして有効にします。どちらも初期状態では**メールは送信されません**。

**実送信の確認（2026-11-27）：** Gmail（`smtp.gmail.com:587`・STARTTLS・アプリ専用パスワード）で、テスト通知1通の送信受付と、利用者本人の受信を確認しました。送信の後、外部通信のスイッチは `False` に戻してあります。Gmailでは、普段のパスワードではなくアプリ専用パスワード（2段階認証が必要）を、空白を入れずに登録してください。ログインが拒否されると `AUTH_FAILED` と表示し、再試行しません。

この文書は、このPC版アプリ（ローカル）のメール通知の仕組みと、長期運用のための部品（履歴の上限・整理・バックアップ）を説明します。クラウド（AWS-B）の通知は別物です。

## 守られること／守られないこと

| 守られること | 守られないこと |
|---|---|
| 初期状態では何も送らない（外部通信のスイッチ `NOTIFY_EXTERNAL_ENABLED` は `False`）。 | 受信されること。「送信受付済み」は、メールサーバーが受け付けたという意味だけです。 |
| 署名付きの許可（あなたの鍵）が、送信のたびに新しく検証される。許可が無い・期限切れ・改ざんなら送らない。 | PC の管理者がファイル（台帳・信頼ファイル）を手で書き換えること。 |
| 宛先・送信元・サーバーは許可の内容そのもの。画面や設定ファイルからは変えられない。 | 実際の通信経路の OS・ネットワークレベルでの隔離（応用層の確認のみ）。 |
| 同じ通知を二重に送らない（結果が不明なときは再送しない）。 | 「必ず1通だけ届く」こと。 |
| パスワード・ユーザー名はどのファイル・ログにも残らない。 | |

## 仕組み

- **設定（秘密なし）**: `<data>/notify/email.json`（チャネル全体のオン/オフ・通知する種類）、`<site>/email-notify.json`（サイトごとのオン/オフ）。**どちらも初期は「オフ」**で、サイトは1つずつ明示的にオンにします。
- **通知する種類**: 障害（FAILURE）／復旧・正常確認（RECOVERY・CONFIRMED）／判定不能（UNKNOWN）／TLS証明書の期限（TLS_*）／画像の変更・失敗（IMAGE_*）。初期はすべてオン。
- **署名付きの通知許可**: `<data>/notify/notify-grant.json` と `.sig`（スキーマ `siteproof.notify-grant.v1`）。HTTP監視の許可・画像撮影の許可とは**別物**で、互いに流用できません。サーバー（ホスト・ポート 465=TLS / 587=STARTTLS）、送信元、宛先（1〜5件）、資格情報の名前、期間（最長366日）、通数の上限（合計・1日）が署名で固定されます。
- **資格情報**: Windows の「資格情報マネージャー」に、**あなたが**汎用資格情報として `SiteProof-SMTP-<名前>` を登録します。SiteProof は送信の瞬間にだけ読み取り、書き込み・保存・ログ出力は一切しません。
- **送信の台帳**: `<data>/trust/notify-ledger/<grant_id>.jsonl`。接続を試みる**前に**1行記録します（合計・直近24時間の上限、読めない行、時計の巻き戻りがあれば送りません）。
- **送信の記録**: `<site>/deliveries.jsonl`（追記のみ）。送る前に ATTEMPT を書き、結果を続けて書きます。途中で止まって結果が無い ATTEMPT は「結果不明」として扱い、**再送しません**。

## 送信のルール

- 有効にした時刻（チャネルとサイトの**遅いほう**）より前の通知は送りません（有効にした瞬間に過去分が一斉に届くことはありません）。24時間より古い通知も送りません（「期限切れ」として1回だけ記録）。
- 結果と扱い: **送信受付済み**（再送しない）／**一部の宛先のみ受付**（再送しない）／**拒否**（5xx・再送しない）／**一時的な失敗**（4xx・接続失敗。5分後、30分後に再試行、最大3回で「再試行の上限」）／**結果不明**（DATA 開始後の失敗。再送しない）／**見合わせ**（許可・台帳・スイッチ・資格情報の問題。何も送っていない）。
- 1回の実行で最大10通。アプリとスケジューラーが同時に動いても、実行は1つずつ（`<data>/notify/dispatch.lock`）。
- テスト送信は、画面から明示的に押したときだけ。1分に1回まで、再試行しません。
- 復旧の通知は、その障害のメールが送られていなくても送られます。

## 使い始める手順（あなたが行う）

1. 先に `tools/setup_monitoring.py` で署名鍵と `trust/allowed_signers` を用意します（このツールは鍵を作りません）。
2. 資格情報マネージャーに `SiteProof-SMTP-main` などの名前で SMTP のユーザー名とパスワードを登録します（SiteProof は触りません）。
3. `py -3.15 -B tools/notify_grant.py --data <データフォルダ> --host <SMTPサーバー> --port 587 --sender <送信元> --recipient <宛先> --credential-ref SiteProof-SMTP-main --days 30 --max-total 500 --max-per-day 20`
   内容を確認して署名します（署名しても通知は始まりません）。
4. 外部通信のスイッチ（`smtp_notify.NOTIFY_EXTERNAL_ENABLED`）は、**安全境界の実測と USER の承認の後**にだけ `True` にします。それまでは、有効化の操作も「無効です」と断ります。
5. アプリでチャネルとサイトをオンにし、テスト送信で確認します。

許可の期限・残り通数が少なくなると、`retention.expiry_notice` が「更新してください」と知らせます（`tools/notify_grant.py` で作り直し）。

## 長期運用の部品（`src/noxiworks/retention.py`）

- **履歴の上限**: `HttpHistory` は 20 MiB / 20 万件で止まります（`HISTORY_FULL`）。何も消さず、書き込みを断るだけです。
- **整理（アーカイブ）**: あなたが明示的に確認したときだけ、履歴・通知・送信記録を `<site>/history-archive/` へ**移動**します（削除ではありません）。操作は `<site>/maintenance-log.jsonl` に残ります。通知を移動しても、過去の通知がもう一度届くことはありません（`notification-keys.txt`）。24時間以内の通知があるあいだは整理できません。
- **使用量**: サイトごと・データ全体のバイト数を領域別に表示できます。
- **観測の空白**: 間隔の2倍を超えて観測が無い期間を一覧にします（未観測の日数も）。
- **止まった理由**: `paused_reason` を、日本語の説明と次にすることに変換します。

## バックアップ（`src/noxiworks/backup.py`、`tools/backup_data.py`）

    py -3.15 -B tools/backup_data.py --data <データフォルダ> --dest <保存先の既存フォルダ> [--site site-xxxxxxxx]
    py -3.15 -B tools/backup_data.py --verify <バックアップのフォルダ>

保存先の**新しい**フォルダ `siteproof-backup-<UTC>` に、ファイルと SHA-256 付きの `MANIFEST.json` を作ります。ローカルのコピーのみで、どこにも送信しません。上書き・削除はしません。リンクはたどらず、秘密鍵（PEM）が見つかったときは何も作らず中止します。`ui/`・`empty/`・`*.lock`・`.tmp-*`・`background/*.log` は含めません。SQLite は一貫したスナップショットを取り、ロック中のものは「コピーしなかった」と報告します。

**復元（手動）**: 先に `--verify` で OK を確認し、バックアップの中身を**新しい空のデータフォルダ**へコピーしてください。既存のデータフォルダへ上書きしないでください。復元の自動処理はありません。
